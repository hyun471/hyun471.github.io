# 에러코드 167개를 정의했는데 76개는 한 번도 쓰이지 않았다

출시 전에 앱과 서버 전체를 훑었다. 문서에 정의된 에러코드가 167개였는데, 그중 76개가 코드 어디에서도 안 쓰이고 있었다.

앱은 잘 돌아가고 있었다. 테스트도 다 통과했다.

## 증상: 실패가 전부 같은 문장으로 보인다

로그인이 실패하면 "로그인에 실패했어요"가 뜬다. 그 문장이 뜨는 경우가 여러 개였다.

- 인터넷이 끊겨 있을 때
- 사용자가 권한을 거부했을 때
- 로컬 저장에 실패했을 때

셋 다 같은 문장이었다. 사용자는 뭘 해야 할지 모르고, Crashlytics에서도 원인이 구분이 안 됐다.

## 원인: enum은 멀쩡했고 연결이 끊겨 있었다

에러코드 enum 자체는 정확하게 구현돼 있었다. 예외 종류를 판별하는 로직도 있었다.

판별 결과를 에러코드로 바꿔주는 변환이 빠져 있었다. 판별은 하는데 그 결과를 버리고 있었던 거다.

여기에 더해 일부 경로는 반환 타입이 `bool`이었다.

```dart
// 실패했다는 사실만 남고, 왜 실패했는지는 사라진다
Future<bool> saveProfile(Profile p) async { ... }
```

`false`를 받은 쪽은 이유를 알 방법이 없다. 그러니 "실패했어요" 하나로 퉁칠 수밖에 없다.

## 왜 아무도 못 잡았나

이게 제일 신경 쓰였던 부분이다. 이 결함은 어떤 자동 검사에도 안 걸린다.

| 검사 | 왜 못 잡나 |
| --- | --- |
| 컴파일 | 문법적으로 완벽하다. enum은 정의만 돼 있어도 된다 |
| 정적 분석 | 안 쓰이는 enum 값은 경고 대상이 아니다 |
| 테스트 | 성공 경로 위주였고, 실패 경로도 "실패했는지"만 본다 |

연결이 없어도 앱은 정상적으로 동작한다. 돌아가는 코드와 의도대로 돌아가는 코드가 다르다는 걸 여기서 봤다.

AI한테 코드를 맡기면 이런 게 잘 생긴다. AI는 컴파일되고 테스트 통과하는 코드를 목표로 잡는다. 문서에 정의된 167개를 전부 배선하는 건 요구하지 않으면 안 한다. 그리고 그 코드를 다시 읽혀도 "잘 짜인 코드"라고 한다. 실제로 문법적으로는 흠이 없으니까.

## 해결

1. 판별 결과를 에러코드로 연결하는 변환을 추가
2. `bool`만 반환하던 경로를 에러코드와 함께 반환하도록 변경
3. 문서에 없는 에러코드를 쓰는 코드를 찾아 양방향으로 정리
4. 에러코드 문서와 앱 enum, 서버 계약을 대조하는 테스트를 추가

앞의 셋은 이번 걸 고치는 작업이고, 4번만 다음을 막는다. 이런 걸 매번 눈으로 세고 싶지 않았다.

## 마치며

정의해둔 것과 배선된 게 달랐다. 문서에 있다고 코드에 있는 게 아니고, 코드에 있다고 호출되는 게 아니었다.

이걸 배포한 뒤에 알았다면 대응할 방법이 없었다. 사용자는 계속 같은 문구만 보고, 나는 Crashlytics를 열어도 원인이 안 보인다. 출시 전 점검을 넣은 게 여기서 값을 했다.
