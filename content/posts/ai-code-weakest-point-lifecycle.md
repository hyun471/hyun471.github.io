# AI가 짠 코드에서 가장 자주 깨지는 건 라이프사이클이었다

같은 원인을 두 프로젝트에서 만났다. 증상은 전혀 달라 보였다.

## 1차: 로딩 화면을 떠났는데 작업이 남아 있다

올해 초 웹 프로젝트에서 이미지 생성 화면을 만들었다. 이 화면에는 세 개가 같이 돈다.

- 생성 요청 비동기 함수
- 진행률 `Timer`
- 진행률 애니메이션

생성 도중에 토큰이 만료되면 인증 상태가 바뀌고, 라우터가 사용자를 메인으로 보낸다. 화면은 사라졌다. 그런데 타이머와 애니메이션은 계속 돌았다. 이미 없는 화면에 접근하려다 에러가 났다.

그때는 이렇게 막았다.

- 화면 종료 여부를 나타내는 플래그를 둔다
- `dispose`에서 `Timer`를 먼저 취소하고 애니메이션을 정리한다
- 비동기 함수는 응답 기다리는 동안 `mounted`로 화면이 살아 있는지 확인한다

고쳐지긴 했다. 그런데 화면마다 같은 처리를 반복해서 넣어야 했다. 화면이 늘어날수록 빼먹을 자리도 늘어난다.

## 2차: 온보딩을 마쳤는데 홈으로 안 넘어간다

개인 프로젝트에서 실기기 버그 5개가 한 번에 올라왔다.

- 온보딩 완료 후 홈으로 안 가고 저장 실패 문구만 뜸
- 로그아웃하면 앱이 종료됨
- 로그아웃 후 재로그인하면 실패
- 온보딩에서 고른 값이 원격 DB에 반영 안 됨

겉보기엔 서로 상관없어 보였다. 그리고 테스트는 전부 통과했다. 실기기에서만 재현됐다.

### 원인은 순서였다

온보딩 완료 처리가 이 순서였다.

```
로컬 저장 → 온보딩 완료 플래그 변경 → 원격 동기화
```

플래그가 바뀌는 순간 라우터가 화면을 전환한다. 이전 화면은 `dispose`된다. 원격 동기화는 그 뒤에 끝난다. 이미 사라진 화면의 `WidgetRef`를 `await` 뒤의 코드가 계속 붙잡고 있었다.

구조 위반도 같이 있었다. 오케스트레이션 코드가 브릿지 impl에 들어가 있었고, 그게 화면의 `WidgetRef`에 묶여 있었다. 규칙 위반이 그대로 버그의 원인이었던 셈이다.

### 이번엔 순서를 바꿨다

1. 로컬 저장과 원격 동기화가 모두 끝난 뒤에 화면 전환을 유발하는 상태 변경을 한다
2. 비동기 작업에서 쓸 `Notifier`를 첫 `await` 이전에 미리 잡아둔다. 화면이 사라진 뒤에는 `WidgetRef`를 다시 안 읽는다
3. 화면 쪽에는 `mounted` 가드를 남겨서 한 번 더 막는다
4. 중복으로 돌던 전역 리스너 2개를 제거

```dart
// 첫 await 전에 잡는다
final notifier = ref.read(userStateProvider.notifier);

await saveLocal();
await syncRemote();

// 여기서 ref를 다시 읽지 않는다
notifier.setOnboardingCompleted(true);
```

1차에서는 증상이 나는 자리마다 막았고, 2차에서는 증상이 안 생기는 순서로 바꿨다.

## 왜 AI는 이걸 못 잡나

AI가 짠 코드를 다시 AI한테 읽히면 "잘 짜인 코드"라는 답이 온다. 이유가 있다.

- 문법적으로 옳다. `await` 뒤에 `ref`를 쓰는 건 컴파일 오류가 아니다
- 테스트를 통과한다. 테스트 환경에는 위젯 트리가 해체되는 타이밍이 없다
- 단위로 보면 다 맞다. 라이프사이클 문제는 화면 수명과 작업 수명의 관계에서 생기는데, 파일 하나만 읽어서는 안 보인다

결국 실기기에서 눌러보고, 어느 순간에 뭐가 죽는지 직접 쫓아가는 수밖에 없었다.

## 마치며

화면의 수명과 작업의 수명은 다르다. 이걸 의식 안 하면 코드가 돌아가는 것처럼 보이다가 실기기에서만 깨진다.

1차에서는 증상만 막고 넘어갔다. 그때 순서를 손봤다면 2차는 같은 형태로 나오지 않았을 것이다.
