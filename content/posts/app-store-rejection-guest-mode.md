# App Store 심사에서 세 번 반려됐다

개인 프로젝트를 App Store에 올리면서 세 번 반려됐다. 마지막 반려 사유가 제일 컸다.

> Guideline 5.1.1(v) — Data Collection and Storage
> 앱의 핵심 기능과 직접 관련이 없으면 계정 등록을 요구할 수 없다.

앱 켜자마자 로그인 요구하지 말라는 얘기다.

## 왜 로그인을 강제했었나

이유는 있었다. 이 앱은 사용자 성향에 맞춰 AI가 계획을 세워준다. 그리고 그 계획의 달성률을 성향별로 분석하려면 계정이 필요하다. 기기를 바꿔도 데이터가 따라와야 하고, 그러려면 원격 DB에 사용자 식별자가 있어야 한다.

그래서 온보딩 → 로그인 → 홈 순서로 짰다. 로그인이 안 되면 앱을 못 쓴다.

Apple 입장은 명확했다. 할 일 적는 기능에 계정이 왜 필요하냐는 거다. 반려 메일을 읽고 나니 맞는 말이었다.

## 처음엔 잘못 접근했다

로그인 화면을 건너뛸 수 있게 하자고 생각했다. 건너뛰기 버튼 달고 나중에 로그인을 유도하는 식으로.

이건 답이 아니었다. 건너뛴 사용자의 데이터를 어디에 둘지, 나중에 로그인하면 그 데이터를 어떻게 합칠지가 안 풀린다. 화면 하나 추가하는 문제가 아니라 데이터 소유자를 누구로 볼 거냐의 문제였다.

## 제한을 두 개로 좁혔다

기능을 하나씩 놓고 이게 계정 없이 되는지 물었다.

| 기능 | 계정 필요? | 이유 |
| --- | --- | --- |
| 할 일 추가·수정·삭제 | 불필요 | 로컬 DB만 있으면 된다 |
| 세부 할 일, 우선순위 계산 | 불필요 | 전부 로컬 연산이다 |
| 오늘의 플랜 | 불필요 | 위와 같다 |
| AI 플래너 | 필요 | 서버에서 사용량을 제한해야 한다 |
| 기기 간 동기화 | 필요 | 원격 DB에 소유자가 있어야 한다 |

세어보니 AI와 동기화 둘뿐이었다. 나머지는 전부 로컬에서 된다.

개수 제한도 안 뒀다. "게스트는 할 일 10개까지" 같은 걸 넣으면 그게 또 우회적인 가입 강요가 된다. 심사에서 또 걸릴 것 같기도 했고.

## 승격은 어떻게 판별하나

게스트로 쓰다가 로그인하면 기존 데이터를 그 계정으로 넘겨야 한다. 문제는 이 사람이 방금 게스트에서 넘어온 사람인지 어떻게 아느냐였다.

온보딩 완료 여부를 기준으로 잡았다. 온보딩을 마친 로컬 데이터가 있는데 지금 막 로그인했다면 게스트가 승격한 경우다. 새 계정으로 처음 들어온 경우와 구분된다.

## 결과

- 로그인 없이 앱의 대부분을 쓸 수 있다
- 심사를 통과했다
- 진입 장벽이 내려갔다. 원래 하려던 것보다 나은 구조가 됐다

## 마치며

반려는 기능을 빼라는 요구가 아니었다. 뭐가 정말 계정을 필요로 하는지 다시 따져보라는 거였다.

따져보니 두 개였고, 처음부터 두 개였다. 기능을 붙여가는 동안 계정이 필요한 범위를 한 번도 다시 확인하지 않은 게 이번 반려의 실제 원인이었다.
