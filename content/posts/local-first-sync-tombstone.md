# JSON 한 덩어리로 저장하다가 동기화에서 막혔다

MVP에서는 사용자 정보와 할 일 구성을 snapshot 형식의 JSON 하나로 저장했다. 구조가 단순하고 빨리 만들 수 있어서 택한 방식이다.

기기 간 동기화를 붙이려는 순간 막혔다.

## 한 덩어리는 부분 변경을 표현하지 못한다

할 일 하나 체크했을 뿐인데 전체 구조를 다시 직렬화해서 통째로 덮어쓴다.

- 뭐가 바뀌었는지 알 수 없다
- 두 기기가 각각 바꾸면 나중에 쓴 쪽이 앞의 걸 전부 지운다
- 간단한 변경이 매번 전체 쓰기라 오류 날 자리가 많다

특히 삭제가 곤란했다. JSON에서 항목이 사라진 것과 애초에 없었던 게 구분이 안 된다.

## 1단계: 구조화된 저장소로

- 로컬은 SQLite (Drift)
- 원격은 Supabase (PostgreSQL)

테이블로 쪼개니 행 단위 변경이 표현된다. 오프라인에서도 앱이 온전히 돌아가야 했기 때문에, 로컬을 임시 캐시가 아니라 1차 저장소로 뒀다.

## 2단계: 로컬 우선 + 변경 대기

쓰기 흐름을 이렇게 잡았다.

```
사용자 작업
  → 로컬 DB에 먼저 저장
  → 화면에 즉시 반영
  → 변경 대기 표시
  → (동기화 시점) 원격과 동기화
  → 대기 표시 해제
```

원격 호출을 매번 하지 않는다. 동기화 트리거는 세 개다. 앱 시작, 하루 경과, 수동 실행.

오프라인이면 대기 상태를 유지하고 로컬 데이터는 그대로 둔다. 연결되면 다시 시도한다.

## 3단계: 삭제는 지우지 않고 표시한다

행을 지우면 원격에 "지웠다"는 사실이 안 남는다. 다른 기기가 동기화할 때 그 항목이 자기 쪽에만 있으니까, 없어진 걸 새 데이터로 알고 다시 올린다. 지운 게 되살아난다.

그래서 삭제는 `deleted_at`에 시각을 남기는 방식으로 바꿨다. 행은 두고 표시만 한다.

## 그리고 데이터가 날아갔다

설계를 다 해놓고도 버그가 났다.

- 로그아웃 후 재로그인하면 마지막에 쓴 할 일이 사라짐
- 로컬 데이터 삭제를 하고 동기화해도 원격에 반영 안 됨
- 지운 데이터가 다른 기기에서 되살아남

원인은 순서였다. 로그아웃과 삭제 처리가 이렇게 돼 있었다.

```
로컬 정리 → 동기화
```

로컬을 먼저 지우니 `deleted_at`을 남길 대상 자체가 없다. 원격에는 삭제가 기록이 안 된다. 다른 기기에서 로그인하면 원격 데이터가 그대로 내려온다.

순서를 뒤집었다.

```
삭제 표시 → 동기화 → 로컬 정리
```

오프라인 로그아웃은 막지 않았다. 대신 동기화가 필요하다는 안내를 띄운다. 로그아웃을 못 하게 막는 건 사용자 입장에서 이상하다.

## 마치며

로컬 우선 설계에서 어려운 건 저장이 아니라 삭제였다. 있는 건 옮기면 되는데, 없어졌다는 사실은 따로 기록해야 전달된다.

설계를 아무리 맞게 해도 순서가 틀리면 데이터가 날아간다는 것도 알았다. 지우기 전에 알려야 한다.
